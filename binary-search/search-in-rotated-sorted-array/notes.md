# Search in Rotated Sorted Array

## Решение

### 1. Поиск pivot + бинарный поиск — O(n) / O(log n), O(1)
Линейно находим точку разворота `k`, затем обычный бинарный поиск со смещением индексов `(k + mid) % n`. Поиск pivot'а линейный — неоптимально.

### 2. Один бинарный поиск — O(log n), O(1)
На каждом шаге определяем какая половина отсортирована, и в зависимости от этого выбираем направление.

```
if nums[low] <= nums[mid] {   // левая половина отсортирована
    if nums[low] <= target < nums[mid] → иди налево
    else → иди направо
} else {                       // правая половина отсортирована
    if nums[mid] < target <= nums[high] → иди направо
    else → иди налево
}
```

### Почему это работает

В ротированном отсортированном массиве хотя бы одна половина ВСЕГДА отсортирована. `nums[low] <= nums[mid]` проверяет левую. Если условие верно — левая целая, можно проверить target в ней. Если нет — разрыв слева, правая целая.

```
Пример: [4,5,6,7,0,1,2], target=0
mid=3 (7): low=4 ≤ 7 → левая [4,5,6,7] сортирована
           target=0 не в [4,7) → направо [0,1,2]
mid=5 (1): low=0 ≤ 1 → левая [0,1] сортирована
           target=0 в [0,1) → налево
mid=4 (0): найдено
```

## Что важно запомнить
- Одна половина всегда отсортирована — ключевой инвариант задачи
- Проверка левой: `nums[low] <= nums[mid]`. Если да → target либо в ней либо в правой
- Проверка правой: когда левая не сортирована → правая точно сортирована → target либо в ней либо в левой
- Границы: `nums[low] <= target < nums[mid]` (левая граница включена, правая нет)

## Что пошло не так
1. Искал pivot линейно — O(n), не использовал структуру поворота
2. Пытался сразу проверять target без проверки какая половина сортирована
3. Путал направление когда target НЕ в сортированной половине
